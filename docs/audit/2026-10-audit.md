# LinuxPlay fork — stability audit (October 2026)

> **Outcome.** Fixes for all of P1/P2 are on branch `stabilize` (one commit
> per change, tests for each): see the [fix plan](2026-10-fix-plan.md) and
> the [before/after measurements](2026-10-measurements.md). N8–N10 were found
> while implementing and measuring, after the first draft of this report.

Scope: the two machines this fork supports, doggoos (KDE Plasma 6 Wayland,
RX 7800 XT, VAAPI HEVC, portal capture) and Danny's MacBook Air (PyAV +
VideoToolbox), linked over Tailscale. Baseline: `9f40df7` + the logging-only
`6cf606c` (`audio-instrumentation`). Inputs: the evidence pack
(`~/linuxplay-audit/linuxplay-audit-evidence.md`, raw logs), the code, and
four experiments run for this audit (§4). Line numbers refer to `6cf606c`.

## 2. Findings

### F1 / N3 — audio dies silently because the host captures the wrong sink · high

**What Danny saw** (his answer): sound gone, video fine, no error, never recovered.

**Host.** `build_audio_cmd()` (`host.py:1934-1963`) runs
`pactl list short sources` once per session and takes the *first* `.monitor`
whose state is `RUNNING`, else the first `IDLE`. That's "whatever happened to
be playing at connect", not "the default sink". Nothing re-checks it, and a
`StreamThread` restart re-uses the same command (`host.py:1035-1069`), so even
an encoder restart can't move to another sink.

- Oct 6 18:27 session (ran until Oct 10 20:06): captured **`wivrn.sink.monitor`**
  (VR in use at connect).
- Oct 11 13:50 session: captured **`alsa_output…hdmi-stereo-extra3.monitor`**.
- A second `wivrn-server` process started **Oct 12 22:26:21**, mid-session.
  When I checked at 18:09 today the default sink was `wivrn.sink` (RUNNING)
  and HDMI was SUSPENDED.

Either direction gives exactly Danny's symptom. Desktop audio follows the
default sink to the headset (or back to HDMI), and the host keeps encoding
the monitor of a now-idle sink, i.e. digital silence. Opus over UDP keeps
flowing, so every check on both ends reads "healthy". If a sink disappears
outright (WiVRn stopping), PipeWire moves the record stream to a fallback
source, which may be a microphone.

**Client.** The `audio_listener` watchdog (`client.py:874-885`) only fires
when ffplay's *clock* stalls. With a live stream of silence the clock advances
and nothing is logged. The 51.8 h log has exactly one audio line after
startup, and the host's encoder never restarted (no `Audio exited` /
`restarting` anywhere). This fits a silent-but-flowing stream, not a dead
player. The instrumentation in `6cf606c` (exit codes, no drop to debug) is
correct but can't see this case.

Evidence quality: circumstantial (no level data exists) but the mechanism is
certain from the code, and the timing lines up. Fix: follow the default sink
(or an explicit `--audio_source`), re-check during the session, detect
silence on both ends, end-of-session audio report.

### F2 — the decode-warning avalanche and the "0 corrupt" counter · high

**What each counter measures** (verified in the lab, §4.1, against the client's own decode settings):

| counter | source | actually counts |
|---|---|---|
| `ts-errors` | `_TSLogCounter` (`client.py:1409-1437`) matching libav log lines | almost only `Packet corrupt (stream = 0, dts = …)`: **one per video frame (PES) that arrived with a hole**. `Continuity check failed` is logged at DEBUG by FFmpeg 8 and never reaches it. Not datagrams, not loss events. |
| `corrupt` | `frame.is_corrupt` on decoder output (`client.py:1313-1320`) | frames with `AV_FRAME_FLAG_CORRUPT`. FFmpeg's HEVC decoder only sets it with `AV_CODEC_FLAG_OUTPUT_CORRUPT`, which the client never sets, so **always 0 by construction**. |
| decode chatter | libav messages passed through to the log | per *refused* frame: 1× `Could not find ref with POC` + 1× `Error constructing the frame RPS` + 3× `First slice in a frame missing` (slices 2-4 have no frame to attach to) + 4× `Skipping invalid undecodable NALU` |

The session log matches that last row exactly: 41,558 / 13,853 = **3.000**
"first slice missing" per RPS error.

**Mechanism.** When a reference picture is lost (a datagram run that takes a
PES start or a whole frame with it), FFmpeg 8.1's HEVC decoder refuses
**every subsequent P-frame until the next IDR** rather than decode against a
missing reference. Refused frames never reach the `is_corrupt` check, so they
look like "the host sent nothing", and the picture freezes on the last good
frame. In the session: 2,188 damaged frames (`ts-errors`) led to 13,853
refused frames, ~6.3 per loss event, ≈0.3% of ~4.5 M frames. Mid-slice
damage that *doesn't* lose a reference is decoded and **displayed with
artefacts, unflagged** (the 21 `CABAC_MAX_BIN` / `cu_qp_delta` errors are
those).

**Transport hypothesis: partly refuted.** `-slices 4` isn't what kills
frames. A lost *reference* does, and slices can't confine that. The slices
only help when the decoder conceals, which it doesn't here. Loss itself is
rare and bursty (N4).

### F3 — teardown race · medium

Confirmed in both disconnects; the briefing's mechanism needs a correction.
The client's `closeEvent` sends `WINDOW_CLOSE 0` **then** `GOODBYE`
(`client.py:2599-2607`). The host's single control thread handles
`WINDOW_CLOSE` first (`host.py:2727-2741`). It pops the last video thread
(without `video_thread_lock`) and joins it for up to ~1.5 s. During that time
`client_ip` is set, the session is active and `video_threads` is empty, which
is exactly the session manager's "start streams" condition
(`host.py:3444-3449`). The manager spawns a fresh ffmpeg + gst feeder
(17:41:28.538). `GOODBYE` (`host.py:2707-2726`) then stops it, and the
manager, seeing no threads after its start call, logs `Streams did not start
(attempt 1)` and arms a retry. The epoch bump clears that retry, so it was
harmless, but it still left an ERROR and a spurious encoder spawn at every
disconnect.

The `GOODBYE` ordering (stop before clearing `client_ip`) is a latent second
window, mostly closed by `last_disconnect_ts` + the 2 s cooldown. The
heartbeat-timeout path (`host.py:3108-3130`) has the same ordering.

**F3 × F6: refuted.** The racing start calls `portal.ensure()`, which returns
at once because the portal session is kept for the host's lifetime
(`portal_capture.py:183-184`). No D-Bus traffic, so no prompt.

**NET switch** (`host.py:2688-2705`): safe from double starts (both callers
serialise on `video_thread_lock` + `starting_streams`), but it runs on the
control thread. A `NET` (or `GOODBYE`) that arrives while the session manager
holds the lock across a 120 s portal dialog **freezes input handling** for that
long. Also, a client that connects in `vpn` mode against a host that last ran
`lan` gets a start → stop → start at session begin (seen Oct 6 18:27:18).

### F4 — stats don't reconcile · medium

| figure | defined in | window | bytes counted |
|---|---|---|---|
| client "x fps" in `Frame pacing` | `updateFrame` (`client.py:1743-1776`) | ~5 s | frames delivered to the renderer |
| "host N fps" | ffmpeg `-progress fps=` (`host.py:831-854`) | **encoder lifetime** (frames ÷ seconds since start) | — |
| "host N Mb/s" | ffmpeg `-progress bitrate=` | **encoder lifetime** | muxed TS bytes |
| "recv N Mb/s" | decoder loop (`client.py:1363-1369`) | last ~1 s before the report (stale if no frames) | elementary-stream payload (no TS/PES headers) |

Proof: across the whole session the host figure tracks the client's
*cumulative* average to ±1 fps (12.8 vs 17 at 13:50, then 26.5/26, 21.3/21 …
24.2/24 at 17:41). The ends agree; the line put a 5 s window next to a 51 h
average. That's why "host 6 fps" sat next to "29 fps" at 14:12. **Decoded fps
varying 10→33 by period is desktop activity, not load** (N5). Host CPU was
1-3% throughout, and low-fps windows have 500-900 ms max gaps with near-zero
recv.

### F5 — off-by-one size chain · low

Real (kscreen rounds 2194.29 up, the portal down) but harmless. The client
maps normalised coordinates × 2195 (`client.py:1816-1843`), uinput's range is
0…2194 (`host.py:2100-2101, 2126-2137`), and KWin scales that range onto its
2194.29 logical width. Worst-case error < 1 logical pixel. No change
recommended. Revisit only if a second monitor gets attached.

### F6 — portal re-prompts · medium

- **The signature the briefing expected will not appear on KDE.** Per the
  ScreenCast spec an unusable `restore_token` "is ignored and the user will be
  prompted normally": `SelectSources` returns 0, and the dialog appears during
  `Start`. So `Portal restore token no longer valid (code N)`
  (`portal_capture.py:256-259`) never fires. The real signature is a `Start`
  that takes human time (Oct 6: 18:27:18 → 18:27:38, 20 s).
- **Tokens are single-use** ("invalidated after using it once"). Anything that
  presents the saved token and doesn't save its replacement kills it. That
  includes a host killed between `Start` and the save, and **`test_portal.py`,
  which negotiates with the production token file**. I triggered this myself
  during the audit: running the suite on doggoos ran it, it waited out its
  120 s dialog timeout, and the token from Oct 6 is now very likely spent.
  **Expect one dialog at the next host start.** Earlier suite runs on the host
  are a plausible cause of past re-prompts.
- `Reusing portal restore token` is logged at DEBUG, so a reuse attempt is
  invisible. `Portal did not issue a restore token…` is printed after
  `SelectSources`, before KDE has had a chance to issue it with `Start` (Oct 6
  printed it, then saved a token 20 s later), which is misleading.
- Unattended: `ensure(timeout_dialog=120)` holds `video_thread_lock` for the
  whole wait (blocking input handling, see F3), the client sees a black screen
  with no explanation, and each session-manager retry raises a new dialog.
- A dead portal session (compositor/portal restart) isn't detected:
  `ensure()` keeps returning the stale session and the feeder keeps failing
  until the host restarts. Not observed; code review only.

### F7 — startup noise · low

Every connect: `PPS id out of range` / `Skipping … NALU` pairs until the first
IDR (slices arriving before any SPS/PPS: the client joins mid-GOP), plus
`not enough frames to estimate rate` / `Could not find codec parameters …
unspecified size` (`probesize=32`, `analyzeduration=0`). Reproduced in the
lab. They're expected and should be summarised, not printed.

### N1 — one VideoToolbox error ⇒ CPU decode for the rest of the session · high

At 14:13:10, 22 minutes in: `vt decoder cb: output image buffer is null:
-12909` → `hardware accelerator failed to decode picture` → `HW decode failed
… switching to CPU`. `client.py:1384-1390` treats *any* exception while
`hwaccel` is set as "this hardware can't decode the stream" and drops it for
good (`_sw_fallback_done`). The lab reproduces it on demand: VT returns
−12909 (`kVTVideoDecoderBadDataErr`) on the first frame whose slice data has
a hole, and the codec context then wedges (`EAGAIN` on every send) until it's
reopened. So a single damaged packet cost hardware decode for 51.5 h, with
more CPU, heat and battery and no visible notice. HW decode was fine; the
input was bad.

*Update after the live measurements:* VideoToolbox also rejects some
**clean** `hevc_vaapi` keyframes. A live recording replayed offline showed
a 321 KB keyframe that FFmpeg's CPU decoder accepts without a message, that
is byte-identical whether reassembled by the client or by FFmpeg's parser,
and that VideoToolbox fails with the same −12909. The 14:13 event had no loss
in its window, so it was probably this. Either way, one rejection must not
cost hardware decode for the session.

### N2 — `--pix_fmt yuv444p` does nothing on this path · low

`hevc_vaapi` only accepts `vaapi` frames. ffmpeg prints `Incompatible pixel
format 'yuv444p' for codec 'hevc_vaapi', auto-selecting format 'vaapi'`,
which `-loglevel error` hides, and encodes **VAProfileHEVCMain, YUV420**
from the `format=nv12,hwupload` chain (`host.py:1790-1792`). The host still
logs `Using requested VAAPI pix_fmt 'yuv444p'` (`host.py:539`). VCN 4 can't
encode 4:4:4 anyway, so there's no cost, no VideoToolbox 4:4:4 question, and
nothing to fix in the pipeline. The log and the launcher should stop implying
otherwise. Related: VBR rate control is told 60 fps (`RC framerate: 60/1`)
while the damage-driven capture averages ~24, so the effective bitrate is
~40% of `--bitrate`, and `-bufsize 15M` (1 s) doesn't meaningfully cap IDR
size.

### N4 — what the loss actually is · info

- No drops anywhere we can count. Host `tailscale0` TX dropped 0,
  `SndbufErrors` 0. Mac `utun10` Ierrs/Drop 0. Tailscale path: **direct over
  the LAN** (192.168.1.98, 5 ms). The Mac is on **Wi-Fi** (802.11ax, 5 GHz
  ch 157/80 MHz, −44 dBm, AWDL up).
- Synthetic burst test (§4.2): bursts of 10-400 back-to-back 1128-byte
  datagrams (up to 450 KB, far beyond any IDR) were **lossless**. The only
  loss was one event of **44 consecutive datagrams**, in a *paced* scenario.
  `full socket buffers` drops during the test: 0.
- Session rate: 2,188 damaged frames in 51.8 h, about one loss event every
  85 s. The test saw one in ~80 s.

So this is a Wi-Fi micro-outage pattern (rare, tens of datagrams at once).
Pacing won't help. Cheap FEC can't cover a 44-datagram run without large
overhead and latency. Retransmission (SRT/ARQ) could, at a fixed latency
cost (a later option, see the plan). The lever that pays now is **recovery
time**. Operational lever, not code: AWDL is a known source of periodic Mac
Wi-Fi stalls.

### N5 — fps measures desktop activity; GOP is counted in frames · medium

The feeder (`pipewiresrc … videorate drop-only=true`) is damage-driven, with
no frames while nothing changes. `-g 15` is counted in frames, so after a lost
reference the freeze lasts "until 15 more damage frames". That's ~0.5 s on a
busy desktop, but seconds on a quiet one (a blinking cursor gives ~2 fps).
The frame you're waiting for is often the one that carried what you just
typed. PipeWire 1.6.8 on the box supports `pipewiresrc keepalive-time`, so a
floor rate (and a time-bounded GOP) is cheap to try.

### N6 — decoder tuning that doesn't happen · low

In `DecoderThread.run` (`client.py:1212-1228`), PyAV 18's `CodecContext` has
no `low_delay` / `strict_std_compliance` attributes, and `flags2` is an int,
so `"+fast"` raises. All are swallowed by `except: pass`. `skip_frame=NONREF`
*does* apply (harmless with this all-reference stream). Cleanup item.

### N7 — tests · medium

On the Mac: `test_autostart` (asserts a `/proc` lookup), `test_parsers`
(asserts the runner is inside a Wayland session), `test_portal` (needs D-Bus)
fail. On doggoos via SSH: `test_parsers`, plus `test_portal`, which is
**destructive** (F6). The suites the brief cited (client A/V, client net) pass.

### N8 — every frame waited for the next two · high

Found while testing the keyframe gate. Replaying the production-encoder clip
over localhost UDP one frame every 300 ms, the client's demux handed each
frame to the decoder **610 ms** after it was sent, two frame intervals.
Two separate holds:

1. ffmpeg's mpegts muxer omits the PES length for video by default
   (`omit_video_pes_length=1`), so the demuxer can't know a frame has
   ended until the next one starts (306 ms with the parser off).
2. FFmpeg's HEVC parser, which the TS demuxer always runs, releases an
   access unit only when it sees the start of the next one (311 ms with
   the length written).

At 30 fps that's +67 ms on every frame. On a damage-driven desktop it's
unbounded: a keystroke on a quiet screen isn't decoded until two more
screen updates arrive. The parser also caused F2's attribution bug: it
moves the transport's corrupt flag onto the frame *before* the damaged
one. Fix: host writes PES lengths (`-omit_video_pes_length 0`), client
demuxes with `noparse` and finds keyframes from the NAL units. Result:
0.7 ms (frames over 64 KB still wait one frame).

### N9 — the audio player was silent for ~4.8 s after every start · medium

ffplay probes a UDP stream for its default 5 s before playing. Every stall
recovery and glitch restart (and, now, every mute toggle) meant ~5 s of
nothing. The TS descriptors already carry what the Opus decoder needs:
with `-probesize 32 -analyzeduration 0` the player plays in 0.2 s.

### N10 — oversized keyframes arrive in pieces without the parser

The TS demuxer cuts a PES of unknown length at 200 KB (`MAX_PES_PAYLOAD`);
the parser used to glue the pieces back together. Real 2194×1234 keyframes
are bigger than that, so the first live run of the N8 fix hit "No start code
is found" on every keyframe and reconnected in a loop. Only the live run
caught it, because the lab clips' keyframes were under 200 KB. The decode
loop now reassembles pieces (each piece after the first lacks a start
code), and `test_client_decode.py` covers a 3 MB keyframe.

## 3. What was checked and found fine

- Host encoder never restarted or logged a warning in the window. Audio
  encoder ran continuously. Host CPU 1-3%.
- No >60 s gaps in 51.8 h of client pacing; decoder never reconnected.
- `udp://` input on the client: 4 MB `SO_RCVBUF` (macOS max 8 MB) + a 24 MB
  FFmpeg receive FIFO; no evidence of socket-buffer drops during tests.
- Path MTU handling (1280 → 1128) is correct; datagrams aren't fragmented.
